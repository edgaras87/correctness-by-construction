## 2. The layers

Knowledge sits in four layers (`temp/common-ground/knowledge-layers-general.md` §2, *The layers*). This section says where each is kept here, and what each holds so far. Layers 1 to 3 are kept in the Maintainer Repo; where inside it is decided when today's Maintainer Repo is brought into this model (`TODO.md`, the item on the layers of knowledge).

The model uses the Common Ground Problem's Defined Terms (`temp/common-ground/common-ground-problem.md`, *Defined Terms*). The picture shortens three: Copy for System Kit Copy, Change for System Kit Copy Change, Update for System Kit Update.

The System Kit is not a layer. It is what is copied to each System Repo, the picture's dashed frame: so far, the System Repos' Adapted Cases of layer 3.

### 2.1 The Backbone Idea layer

Layer 1 holds Backbone Ideas (`temp/common-ground/knowledge-layers-general.md` §2.1, *The Backbone Idea layer*). Each row's description is a summary; the idea's home holds it.

| Backbone Idea | What it says | Home |
|---|---|---|
| The layers of knowledge | the layers knowledge sits in, and how it moves between them | `temp/common-ground/knowledge-layers-general.md` |
| How an agent works | what one piece of agent work is: what the agent does, when, where and how | planned, from `docs/models/agent.md` (`TODO.md`, the item that rewrites the Agent Model) |

Which other of today's project-agnostic ideas are Backbone Ideas is open (§4).

It is kept in the Maintainer Repo, and stays there. A System Repo receives it only adapted, in the System Kit.

### 2.2 The Work Domain layer

Layer 2 holds Work Domain Ideas (`temp/common-ground/knowledge-layers-general.md` §2.2, *The Work Domain layer*), each a Backbone Idea of §2.1 adapted to one Work Domain.

The Maintainer Repo works in one Work Domain, keeping knowledge. A System Repo works in two so far: designing a backend by CBC, its problem, and keeping its own knowledge. So keeping knowledge is worked in every repo. The Maintainer Repo keeps the texts of both Work Domains, the picture's two boxes. Keeping the System Repos' texts is part of its own work (§3.2).

In each table, a row's description is a summary; the idea's home holds it. Whether the two Work Domain Ideas of how an agent works differ is open (§4).

### 2.3 The Adapted Case layer

Layer 3 holds Adapted Cases (`temp/common-ground/knowledge-layers-general.md` §2.3, *The Adapted Case layer*), each written from a Work Domain Idea of §2.2.

Here an Adapted Case is one piece of agent work, such as reading a System Repo, working one step of its Plan Step, or writing a commit message. Its instruction text is an Agent Skill or an Agent Rule; how many one Adapted Case holds is open (§4). Its understanding text says why the instruction text is as it is. The agent uses the instruction text in the work, and reads the understanding text only when the instruction text is changed. The two travel together: a System Repo's Copy holds both.

Layer 3 is split like layer 2: one part for each Work Domain. The Maintainer Repo keeps both. Keeping knowledge's part holds two groups, the picture's two right boxes (§2.3.1). An Agent Skill or Agent Rule found in two groups is two Adapted Cases, one in each. The two are tied only through the nearest idea above them both (`temp/common-ground/knowledge-layers-general.md` §2.3, *The Adapted Case layer*).

An Adapted Case may also be written by work no Adapted Case covers, on trial: one kind of Knowledge on Trial (`temp/common-ground/knowledge-layers-general.md` §3.2, *The arrows*, the arrow *change*). Either repo writes it. A System Repo's Knowledge on Trial is kept in the System Repo, comes from no Copy, and is handed over at its close.

#### 2.3.1 Keeping knowledge

Two groups so far:

- **Its own,** the Maintainer Repo's, for itself. So far, apart from its Approaches on Trial, all are written from one Work Domain Idea of §2.2.1: how an agent works, keeping knowledge. The Maintainer Repo works by them in place, with no Copy (§2.4). If a Maintainer Kit is wanted, it is made from them (§4, question 1).
- **The System Repos',** for keeping a System Repo's own knowledge, such as taking an Update. They are written from §2.2.1's Work Domain Ideas, and are part of the System Kit (§2.3.2).

#### 2.3.2 Designing a backend by CBC

The System Repos' Adapted Cases for designing a backend, in two groups so far, one for each Work Domain Idea of §2.2.2:

- **Agent work,** from how an agent works, designing a backend.
- **CBC system design,** from CBC design for backends. How it meets agent work in one Adapted Case is open (§4).

With the System Repos' group of §2.3.1, they are the System Kit. Each System Repo works from Copies of them (§2.4).

### 2.4 The layer of a repo's work

Layer 4 is work done by an Adapted Case (`temp/common-ground/knowledge-layers-general.md` §2.4, *The layer of work*). The text it works by is a layer-3 text, wherever it is kept. Whether what the work makes is layer 4 is open (§4). Here the work is a repo's:

- **Each System Repo's work, by its Copies:** a System Repo is born with Copies of the System Kit and works by them. A Copy is a layer-3 text kept in the System Repo. As its work needs, it makes Changes, so its Copies differ from the System Kit on purpose. It is kept outside the Maintainer Repo, so every arrow between it and layer 3 crosses from one repo to the other.
- **The Maintainer Repo's own work:** the Maintainer Repo works by its own Adapted Cases in place, with no Copy: they are kept where the work is done, so nothing is delivered. There, layer 3 and the work are in one repo, the double line *used in place*. A change its work makes is, at once, a change to its Adapted Case. Its problem is keeping this knowledge, as a System Repo's is designing one system.

## 3. How knowledge moves

How knowledge enters the layers and moves between them is the general document's (`temp/common-ground/knowledge-layers-general.md` §3, *How knowledge moves*). This section adds the arrows between the Maintainer Repo and the System Repos, and how a Change travels them.

### 3.1 The arrows

- **adapt,** **lesson** and **set apart,** between layers 1, 2 and 3: as the general document has them (`temp/common-ground/knowledge-layers-general.md` §3.2, *The arrows*). A lesson, or a part set apart, can come from either column.
- **birth,** layer 3 to layer 4: a new System Repo receives Copies of the System Kit, at one System Kit Version.
- **Update,** layer 3 to layer 4: the System Kit's changes since a System Repo's Copies were taken. The System Repo takes them by its own Copy of the Adapted Case for taking them.
- **Change, read back,** layer 4 to layer 3: a System Repo changes a Copy and records why. The Maintainer Repo reads it back and judges it against the Adapted Case the Copy came from.
- **used in place,** layer 3 and layer 4 in one repo, with no Copy: the Maintainer Repo's own work changes its own Adapted Cases directly.

### 3.2 How a Change moves

The simulation follows one System Repo's Change through six parts (`temp/common-ground/system-repo-change-simulation.md` §1, *How it is worked*). Each part sits at a layer, or on an arrow:

| Part | Who | Where in the picture |
|---|---|---|
| Change | System Repo | layer 4, in a Copy |
| Read | Maintainer Repo | the arrow *Change, read back* |
| Judge | Maintainer Repo | layer 3: which layer the Change holds for |
| Act on the verdicts | Maintainer Repo | the layer the verdict names; the arrows *lesson* and *adapt* |
| Deliver | Maintainer Repo | the arrow *Update* |
| Take | System Repo | layer 4, its Copies |

So the six parts are one movement: up from layer 4, as high as the Change holds, and back down.

The simulation's depths say how high a Change goes (`temp/common-ground/system-repo-change-simulation.md` §2, *The cases*). They name the project-agnostic text, which here is layer 2 or layer 1:

| Depth | Highest layer it changes | Arrows it travels |
|---|---|---|
| a. it stays in the System Repo | layer 4 | *Change, read back*; nothing comes down |
| b. the System Kit's Adapted Case changes | layer 3 | *Change, read back*; *Update* |
| c. the project-agnostic text changes | layer 2 or layer 1 | *Change, read back*; *lesson*; *adapt*, to every text built on that idea, the Maintainer Repo's own among them; *Update* |
| d. the project-agnostic text already holds it | layer 3, fixed from the layer above | *Change, read back*; *adapt*; *Update* |
| e. it asks to narrow the project-agnostic text | layer 3, marked; the layer above stays | *Change, read back*; *Update* |
| f. several Adapted Cases need it, but not all | layer 2, if they share a Work Domain | *Change, read back*; *lesson*; *adapt*; *Update* |

The Work Domain layer fills part of depth f's gap: text shared by the Adapted Cases of one Work Domain has a layer. Text shared across Work Domains, but not by all, still has none.

### 3.3 The Maintainer Repo's lessons

A lesson from the Maintainer Repo's own work starts in layer 4 of the right column. Since that work is done by its own Adapted Cases in place, the lesson changes layer 3 at once. It is then judged by the same questions 3 and 4 as a Change read back, and goes up the arrow *lesson* as far as it holds (`temp/common-ground/common-ground-problem.md` §2.1, *Judging a change read back*). If it reaches layer 1, it comes down the arrow *adapt*, to the System Repos' Adapted Cases too, and reaches System Repos by an Update.

It has no Read, Deliver or Take of its own: nothing crosses between repos until an Update carries it to a System Repo.

## 4. Open questions

None is answered by the text above. Each is answered when work reaches it: its answer goes into the text above, and the question leaves this list.

1. **A Maintainer Kit:** should there be a kit a new Maintainer Repo is born from, as a System Repo is born from the System Kit? There is one Maintainer Repo so far. The Tiers Model has a rule for a second Concept Repo (`docs/models/tiers.md` §2.1, *The empty top tier*), and `cbc-concept`, built by the stopped Plan Step *Rebuild in cbc-concept*, is close to a second Maintainer Repo. §2.3.1 says what a Maintainer Kit would be made from.
2. **What layer 4 holds:** the general document's question (`temp/common-ground/knowledge-layers-general.md` §4, *Open questions*, question 6). Here it is met at a System Repo's design of its system and its own Knowledge on Trial.
3. **A name for the movement:** what runs from a Change to the take of the next Update, as one thing (§3.2), so the simulation can name it.
4. **The depths and the layers:** is how deep a Change goes the same as how high it goes (§3.2)? Text shared across Work Domains, but not by all, is the general document's question (`temp/common-ground/knowledge-layers-general.md` §4, *Open questions*, question 1). Here it is met when the open Plan Step's stage 2 labels which parts of `concept/` are which.
5. **Where Judge sits:** §3.2 puts it at layer 3, since a Change is judged against the Adapted Case its Copy came from. The sources say only that it runs in the Maintainer Repo.
6. **Depth d and the layer above:** if several Adapted Cases lost the same part, the layer above may be reworded clearer (`temp/common-ground/system-repo-change-simulation.md` §2, *The cases*). §3.2's row leaves it out.
7. **What then points at it:** the simulation's opening and the problem file's §2.1. Then `temp/`'s old files, one by one, and how today's ways are written across the drafts.
8. **What the System Kit holds:** layer 3 only, or the System Repos' Work Domain Ideas too. CBC system design adapted for backends (`temp/common-ground/common-ground-problem.md` §2.1, *What the System Kit holds*, item 2) may already be layer 2.
9. **Which other ideas are Backbone Ideas:** of today's project-agnostic ideas, beyond how an agent works and CBC design (§2.1).
10. **What one Adapted Case holds:** one Agent Skill or Agent Rule under its understanding text, or several. One understanding text may stand under more than one, as the facts-in-sync manual stands under two Agent Rules.
11. **Two Work Domain Ideas of how an agent works:** does an agent's work differ enough between keeping knowledge and designing a backend by CBC to need two texts, or would they be one text written twice (§2.2)?
12. **An Adapted Case from two ideas:** the cbc-framing Agent Skill holds CBC design's content, written as a piece of agent work. Is it adapted from two Work Domain Ideas, or from one, with the other giving only its form?
13. **When a change is judged:** a System Repo's Change is judged before it reaches layer 3 (§3.2). The Maintainer Repo's own change reaches layer 3 at once, and is judged after (§3.3). Does the difference matter? The change work answers it.
14. **Knowledge on Trial offered back:** a System Repo's Knowledge on Trial is handed over at its close (§2.3). It is not a Change, so the arrow *Change, read back* does not carry it, and the picture has no arrow that does. The change work answers it, when the simulation takes its other sources.
